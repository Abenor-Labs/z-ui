# Plan: `@abenor/z-ui`, the CLI

**Status:** draft, awaiting approval
**Date:** 2026-08-06
**Closes roadmap items:** 8 (`init`, `add`, `list`) and 11 (publish)

---

## Why this is next

Every page of the site leads with `npx @abenor/z-ui add <name>`. That command
does not exist. Until it does, the site markets a promise nothing keeps, and no
amount of design work on the showcase changes that.

[ROADMAP.md](../ROADMAP.md) sequences `copy-button` (item 7) before the CLI
(item 8), on the reasoning that "a contract validated by a single component is a
coincidence." Ten components now exist across all three v1 categories. That
gate is over-satisfied and the note is stale; the CLI is unblocked.

## The test this has to pass first

[ADR 0002](../adr/0002-first-party-cli-with-shadcn-compatible-manifests.md) sets
an explicit kill condition:

> If, once written, the CLI does nothing shadcn's does not, it should be dropped
> rather than maintained. The test is whether `add` has at least one behaviour
> that a general-purpose registry client could not provide.

Three candidate behaviours, all real, none available from a general client:

1. **Install-time spring selection.** `z-ui add like-button --spring settle`
   rewrites the component's default preset before the file is written. A generic
   registry client copies bytes; it has no concept of a spring scale.
2. **Digest verification.** The generator already computes a sha per file and
   publishes it in the manifest. `add` verifies the bytes it received against
   that digest and refuses on mismatch. This is the claim the site makes on every
   component page — "byte-identical to the repository" — enforced rather than
   asserted.
3. **Reduced-motion audit.** `z-ui doctor` checks that every installed component
   still routes through `useZTransition`, catching the most likely way someone
   silently breaks the accessibility contract while editing their own copy.

**If we build this and none of the three survive contact, ADR 0002 says delete
the package.** That is the honest bar and this plan accepts it.

## Non-goals

Recorded so they do not get relitigated mid-build.

| Not doing | Why |
| --- | --- |
| Tailwind config merging | Components ship utility classes only. Nothing to merge. |
| `tsconfig.json` alias resolution | ADR 0002 avoids it deliberately: `z-ui.json` stores the import specifier and the disk path explicitly. This is the single largest cost of a first-party CLI and we are not paying it. |
| A `registry:base` / whole-design-system payload | shadcn v4 added this. We have no theme, no CSS variables, no fonts to install. |
| Version pinning / semver on registry items | ADR 0003 accepts `main`-only for now. Revisit when someone asks. |
| Interactive component browser in the terminal | The site is the browser. |
| Telemetry | PRODUCT.md. No server, nothing to collect. |

## Package layout

`packages/` is declared in [pnpm-workspace.yaml](../../pnpm-workspace.yaml) but
does not exist yet.

```
packages/cli/
  package.json          name @abenor/z-ui, bin { "z-ui": "./dist/index.js" }
  src/
    index.ts            arg parsing, command dispatch
    commands/
      init.ts
      add.ts
      list.ts
      doctor.ts
    registry/
      fetch.ts          URL or local path, one code path
      resolve.ts        registryDependencies graph, cycle-safe
      verify.ts         sha check against the manifest
    project/
      config.ts         read/write/validate z-ui.json
      write.ts          targets, overwrite policy, dry-run
      deps.ts           npm dependency install via detected package manager
    ui/
      log.ts            one output surface, honours --silent
      prompt.ts
  test/
    fixtures/           a fake project + a local registry
```

Runtime dependencies kept deliberately small: an arg parser, a prompt library, a
colour library. No framework. The CLI must start fast — it is invoked through
`npx` on a cold cache.

## `z-ui.json`

The foundation spec (PR #1) is unmerged and not in this repo, so this shape is
designed from the constraints ADR 0002 already fixed. **Reconcile at merge.**

```jsonc
{
  "$schema": "https://raw.githubusercontent.com/Abenor-Labs/z-ui/main/registry/schema/config.schema.json",

  // URL or local path. One string, so moving to a hosted origin is a config
  // edit and no code change. (ADR 0003)
  "registry": "https://raw.githubusercontent.com/Abenor-Labs/z-ui/main/registry",

  // Both halves stated explicitly. This is what buys us out of tsconfig
  // resolution entirely: `alias` is what gets written into import statements,
  // `dir` is where bytes land on disk. `init` guesses once and confirms.
  "paths": {
    "components": { "alias": "@/components/z-ui", "dir": "components/z-ui" },
    "hooks":      { "alias": "@/hooks",           "dir": "hooks" },
    "lib":        { "alias": "@/lib",             "dir": "lib" }
  },

  "spring": "snap",        // default preset applied by --spring when omitted
  "typescript": true       // false writes .jsx and strips types
}
```

A `config.schema.json` ships alongside the existing registry schemas so the file
is validated in CI and autocompletes in editors.

## Commands

### `z-ui init`

1. Refuse to run twice unless `--force`.
2. Detect the framework and source layout — `src/` vs root, app vs pages — to
   propose defaults rather than demand answers.
3. Detect the package manager from the lockfile.
4. Prompt for each `paths` entry with the guess pre-filled, and for `typescript`.
5. Write `z-ui.json`. Write nothing else.

Flags: `--yes` (accept every guess), `--registry <url|path>`, `--cwd`.

### `z-ui add <name...>`

The whole product. Ordered so that nothing is written until everything is known
to be writable.

1. Load and validate `z-ui.json`. Absent → offer to run `init` first.
2. Fetch each named item. `--registry ./registry` reads from disk, which is what
   makes contributor testing and a network-free test suite possible.
3. Resolve `registryDependencies` transitively, deduplicated, cycle-safe.
4. Verify every file's bytes against its manifest `sha`. Mismatch aborts before
   any write, naming the file.
5. Map each file's `target` through `paths` to a real destination.
6. Rewrite imports: the `@/` specifiers in registry source become the consumer's
   configured `alias`. Pure string substitution against known keys, no AST.
7. If `--spring` is passed, rewrite the component's default preset.
8. Report the full plan — files to create, files to overwrite, npm packages to
   install — then confirm. `--dry-run` stops here. `--yes` skips the prompt.
9. Write files. Existing files prompt individually unless `--overwrite`.
10. Install npm `dependencies` with the detected package manager.

Flags: `-y --yes`, `-o --overwrite`, `--dry-run`, `--spring <preset>`,
`-r --registry <url|path>`, `-c --cwd <dir>`, `-s --silent`.

Following shadcn's flag names where they overlap is deliberate — it is the
convention the audience already has in their fingers.

### `z-ui list`

Prints the registry index: name, category, spring, state count. `--json` for
scripting. This is the command that makes the CLI usable without the website.

### `z-ui doctor`

Scans installed components and reports: files that drifted from their published
digest, components no longer routing through `useZTransition`, and missing npm
dependencies. Read-only; it never edits.

## Failure behaviour

Most of the quality of a CLI is what it does when something is wrong.

| Situation | Behaviour |
| --- | --- |
| No `z-ui.json` | Explain, offer `init`, exit 1 |
| Unknown component | Show the closest matches from the index, exit 1 |
| Registry unreachable | Name the URL and the status, suggest `--registry` for local, exit 1 |
| Rate limited by raw GitHub | Say so explicitly — it is a documented limit of ADR 0003, not a bug the user caused |
| Digest mismatch | Abort before writing anything, name the file, exit 1 |
| File exists | Prompt per file; `--overwrite` to skip prompting; never silently clobber |
| Partial write then failure | Report exactly which files landed. No rollback — a half-install the user can see beats a silent revert |

Exit codes: `0` success, `1` user-correctable, `2` internal.

## Testing

- Unit: dependency graph resolution including cycles, import rewriting, digest
  verification, config validation.
- Integration: a fixture project plus `--registry ./registry` pointed at this
  repo. Runs offline, and asserts the written bytes equal the registry source.
- The integration test is also the answer to "does the CLI still work after a
  component changes" — it runs in CI on every PR that touches `registry/`.

## Publish

1. `packages/cli` builds to `dist/` with a shebang and `bin` wired.
2. Verify the `@abenor` scope is owned. **Needs your npm account — I can build
   and verify locally but the publish itself is yours to run.**
3. `npm publish --access public --dry-run` first, inspect the file list.
4. Publish `0.1.0`.
5. Smoke test from a scratch project: `npx @abenor/z-ui@latest init` then `add`.

## What changes on the website afterwards

- The install block drops the shadcn tab from the *advertised* path. Manifest
  compatibility stays — it is free and it is a real hedge — but our own command
  becomes the only one shown.
- `unpublished` badges come off.
- The fabricated `z-ui.abenor.dev` URL in the concept mock gets corrected; the
  real registry is the raw GitHub base until a domain exists.
- Docs gains an `init` → `add` → edit walkthrough.

## Sequencing

| Step | Deliverable |
| --- | --- |
| 1 | `packages/cli` scaffold, `z-ui.json` + schema, `list` |
| 2 | `add` end to end against `--registry ./registry`, with tests |
| 3 | `init` with detection and prompts |
| 4 | Digest verification, `--spring`, `doctor` — the three ADR-0002 justifications |
| 5 | Publish, then the website edits above |

Steps 1–2 are the ones that make the site true. Steps 4 is the one that makes
the package worth existing rather than deferring to shadcn.
